This example starts with a script that answers one question:
"What was revenue last week?" The script runs a SQL query and prints the
result.

```python
answer = run_sql("SELECT SUM(amount) FROM orders WHERE week = '2026-W35'")
print(answer)
```

The result may still be wrong. If last week's order file was loaded twice,
the script adds the same orders twice. It has no check that can detect this
from the total alone.

The version below adds a loop around the script. It reads information about
the table before writing SQL, checks the data, and stops after three failed
attempts.

## Read the table before writing SQL

The program first reads the table schema. The model needs to know whether the
amount is stored as `amount` or `amount_cents`. It also needs to know whether
the table has a `status` column that should be filtered.

```python
columns = run_sql("""
    SELECT column_name FROM information_schema.columns
    WHERE table_name = 'orders'
""")
query = ask_model("What was revenue last week?", columns)
```

The `ask_model` line receives the question and the column names, then writes
SQL. It is the only language-model call in this example. The other steps use
ordinary code.

## Check the data before returning the answer

A model can write valid SQL and still use duplicated data. Before returning
the result, the program compares the total row count with the number of
distinct order IDs.

In this example, each order should have one row. The two
counts should therefore match.

```python
def check(week):
    counts = run_sql(f"""
        SELECT COUNT(*) AS total, COUNT(DISTINCT order_id) AS ids
        FROM orders WHERE week = '{week}'
    """)
    if counts.total != counts.ids:
        return f"orders has duplicates: {counts.total} rows, {counts.ids} order ids"
    return None
```

This rule belongs to this particular table. A generic type check would not
find the duplicated load. Other checks can compare the row count with last
week or compare the result with the payment provider's total. Each check
should represent a rule that is valid for the data.

## Retry with a limit

If the check fails, the function adds the problem to its notes and asks the
model for another query. It allows up to three attempts. After that, it
stops and returns the notes instead of an unverified number.

```python
def data_agent(question, week, tries=3):
    notes = [describe_table("orders")]          # 1. look
    for attempt in range(tries):
        query = ask_model(question, notes)      # 2. act (the only model call)
        result = run_sql(query)
        problem = check(week)                   # 3. check
        if problem is None:
            return result, notes
        notes.append(problem)                   # 4. learn, then go again
    return None, notes                          # 5. stop, and say why
```

In the intended second attempt, the model sees the note
`orders has duplicates` and writes a query with one row per order ID. The
check then runs again. A real model is not guaranteed to make the correct
revision, so the function keeps the attempt limit and returns its notes when
the checks continue to fail.

## Keep data changes separate

Many agent frameworks arrange work around a similar loop and add features
such as logging and retry budgets. The framework does not know which checks
are correct for a warehouse. Those rules come from the data model. In this
example, one row should represent one order.

The agent does not delete duplicated rows or change the source table. It
changes only the query used for this answer and records the duplicate it
found. Repairing the data load is a separate action that requires the right
permission.

Before using this pattern, define the checks and the failure limit. Without
a check, a program can return a plausible total from incorrect data.
