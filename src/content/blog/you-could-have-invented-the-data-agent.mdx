Suppose your manager asks for last week's revenue. You could answer with
a short SQL query:

```python
answer = run_sql("SELECT SUM(amount) FROM orders WHERE week = '2026-W35'")
print(answer)
```

The query can run successfully and still return the wrong total. If the
order file was loaded twice, it counts every order twice. Nothing in this
script checks for that.

A data agent can inspect the tables, write a query, and use checks to
decide whether to return a result or investigate further. The following
examples outline that process but are not a complete application.

## 1. Inspect the table

Before writing SQL, check the columns and their meaning. Is the amount
stored in euros or cents? Does revenue include every order status, or
only paid orders?

```python
columns = run_sql("""
    SELECT column_name FROM information_schema.columns
    WHERE table_name = 'orders'
""")
query = ask_model("What was revenue last week?", columns)
```

Here, `ask_model` receives the question and column names and generates
SQL. Table inspection and query execution are ordinary code. In practice,
column names alone may not explain the business definition of revenue.

## 2. Check the data

For a table with one row per order, compare the row count with the number
of distinct order IDs. A mismatch is a reason to investigate before using
the total.

```python
def check(week):
    counts = run_sql(f"""
        SELECT COUNT(*) AS total, COUNT(DISTINCT order_id) AS ids
        FROM orders WHERE week = '{week}'
    """)
    if counts.total != counts.ids:
        return f"orders has duplicates: {counts.total} rows, {counts.ids} order ids"
    return None
```

This check does not use a language model. Other useful checks might compare
row counts with the previous week or reconcile revenue with a payment
provider. The right checks depend on what each table represents.

## 3. Limit retries and report failures

An agent can pass a failed check back to the model as context for another
attempt. The loop also needs a limit so it can stop and explain what went
wrong.

```python
def data_agent(question, week, tries=3):
    notes = [describe_table("orders")]          # 1. look
    for attempt in range(tries):
        query = ask_model(question, notes)      # 2. act (the only model call)
        result = run_sql(query)
        problem = check(week)                   # 3. check
        if problem is None:
            return result, notes
        notes.append(problem)                   # 4. learn, then go again
    return None, notes                          # 5. stop, and say why
```

There is an important limit in this example: `check(week)` examines the
source table, not the query result. If the source still has duplicate
orders, changing the query will not make this check pass. The loop will
stop after three attempts and return its notes.

A result-level check or an approved correction to the source would be
needed to resolve that problem. Retrying alone does not repair data.

## What this example covers

The example shows how a model call can sit inside a controlled process.
The model proposes SQL, while code runs the query, performs checks, and decides
whether to continue.

The duplicate check covers one specific problem. Passing it does not prove
that the query uses the right dates, filters, or revenue definition. Those
need their own checks. The loop also has no permission to change the source
tables, so any data repair remains a separate task.
