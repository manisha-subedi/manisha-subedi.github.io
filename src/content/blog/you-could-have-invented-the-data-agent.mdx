Let's say your manager asks you: what was revenue last week? You have a
database and you know SQL. So you write a script.

```python
answer = run_sql("SELECT SUM(amount) FROM orders WHERE week = '2026-W35'")
print(answer)
```

It works. It prints a number. But there is a problem. It prints a number
even when the number is wrong. If somebody loaded last week's order file two
times, the script counts every order twice. It does not know. It cannot know.

People say the answer to this is an "AI data agent". That sounds big. But I
think you can build one yourself, with the script you already have. There
are only three ideas in it.

## 1. Look at the table first

A good analyst does not start with the query. She starts by looking at the
table. What columns are there? Is the money in `amount` or in `amount_cents`?
Is there a `status` column I should filter on?

So the agent looks first.

```python
columns = run_sql("""
    SELECT column_name FROM information_schema.columns
    WHERE table_name = 'orders'
""")
query = ask_model("What was revenue last week?", columns)
```

The `ask_model` line is the only place where a language model is used. It
gets the question and the column names, and it writes the SQL. Everything
else is normal code that you write one time.

## 2. Check the answer

Now we have a query written by a model. Let's not trust it. And let's not
trust the data either. The cheapest check I know is this: count the rows,
and count the different order IDs. In a clean orders table, these two numbers
are the same.

```python
def check(week):
    counts = run_sql(f"""
        SELECT COUNT(*) AS total, COUNT(DISTINCT order_id) AS ids
        FROM orders WHERE week = '{week}'
    """)
    if counts.total != counts.ids:
        return f"orders has duplicates: {counts.total} rows, {counts.ids} order ids"
    return None
```

Notice that the check has nothing to do with the model. It is plain SQL
about your data. You can add more checks like this. Compare the row count
with last week. Compare the total with the payment provider. Each one is a
few lines. Each one catches something a type check never will.

## 3. Try again, but not forever

What happens when the check fails? A normal script crashes, or prints the
wrong number with full confidence. An agent takes the problem, adds it to
its notes, and tries again. But not forever. Three tries, then it stops and
says why.

Put the three ideas together and you get this:

```python
def data_agent(question, week, tries=3):
    notes = [describe_table("orders")]          # 1. look
    for attempt in range(tries):
        query = ask_model(question, notes)      # 2. act (the only model call)
        result = run_sql(query)
        problem = check(week)                   # 3. check
        if problem is None:
            return result, notes
        notes.append(problem)                   # 4. learn, then go again
    return None, notes                          # 5. stop, and say why
```

That's it. That is the agent. On the second try, the model sees the note
"orders has duplicates" and writes the query with one row per order. On the
third try it either passes the check, or it gives you the notes instead of a
number.

## What you just built

Look at the loop one more time. Look, act, check, learn, stop. Every agent
framework you can buy is this loop, with more logging and a nicer logo. That
is fine. But the useful part is not the model call. It is the `check`
function. Nobody can sell you that one, because it is about your data. Only
you know what normal looks like in your tables.

Also notice what the agent does not do. It does not delete the duplicate
rows. It does not fix the table. It works around the problem and tells you
what it found. Fixing the data is a job for a person with permission, not
for a loop with three tries.
