Picture this. It's Monday morning. Your manager writes: "What was revenue
last week?" You have a warehouse, you know SQL, and you would like to be done
before your coffee gets cold.

So you write a script.

```python
answer = run_sql("SELECT SUM(amount) FROM orders WHERE week = '2026-W35'")
print(answer)
```

It works. It prints a number. It also has one small problem: it prints a
number even when the number is wrong. If somebody loaded last week's order
file twice, the script prints double. It doesn't know. It can't know. It has
no way to look.

People will tell you the answer to this is an "AI data agent". Big words. But
I think you could have invented the data agent yourself, on that Monday, with
the script you already have. There are only three ideas in it.

## Idea 1: look before you act

The first thing a good analyst does is not writing the query. It's looking at
the table. What columns are there? Is it `amount` or `amount_cents`? Is there
a `status` column I should filter on?

So the agent looks first.

```python
columns = run_sql("""
    SELECT column_name FROM information_schema.columns
    WHERE table_name = 'orders'
""")
query = ask_model("What was revenue last week?", columns)
```

That `ask_model` line is the only place in this post where a language model
shows up. It gets the question and the column names, and it writes the SQL.
Everything else is normal code that you write once and keep.

## Idea 2: check the answer

Now we have a query written by a model. Let's not trust it. Let's not trust
the data either. The cheapest check I know is this: count the rows, and count
the distinct order ids. In a clean orders table, those two numbers are equal.

```python
def check(week):
    counts = run_sql(f"""
        SELECT COUNT(*) AS total, COUNT(DISTINCT order_id) AS ids
        FROM orders WHERE week = '{week}'
    """)
    if counts.total != counts.ids:
        return f"orders has duplicates: {counts.total} rows, {counts.ids} order ids"
    return None
```

Notice that the check has nothing to do with the model. It's plain SQL, and
it's about your data. You can add more of these: compare the row count with
last week, compare the sum with the payment provider's total. Each one is a
few lines. Each one catches something a type test never will.

## Idea 3: learn, try again, and know when to stop

What happens when the check fails? A script crashes, or prints the wrong
number with full confidence. An agent takes the finding, adds it to what it
knows, and tries again. But not forever. Three tries, then it gives up and
says so.

Put the three ideas together and this is what you get:

```python
def data_agent(question, week, tries=3):
    notes = [describe_table("orders")]          # 1. look
    for attempt in range(tries):
        query = ask_model(question, notes)      # 2. act (the only model call)
        result = run_sql(query)
        problem = check(week)                   # 3. check
        if problem is None:
            return result, notes
        notes.append(problem)                   # 4. learn, then go again
    return None, notes                          # 5. stop, and say why
```

That's it. That's the agent. On the second try, the model sees the note
"orders has duplicates" and writes the query with one row per order id. On
the third try it either passes the check, or it hands you the notes instead
of a number.

## What you just built

Look at the loop once more. Look, act, check, learn, stop. Every agent
framework you can buy is this loop with more logging, a retry budget, and a
nicer logo. Nothing wrong with that. But the part that makes it useful is not
the model call. It's the `check` function. And nobody sells you that one,
because it's about your data, and only you know what normal looks like in
your warehouse.

Also notice what the agent does not do. It does not delete the duplicated
rows. It does not "fix" the table. It works around the problem and tells you
what it found, in the notes. Fixing the load is a job for a person with
permission, not for a loop with three tries.

So next time someone shows you an agent demo, look for the check. If there is
none, you are looking at the first script, the one that prints a number even
when it's wrong. And if you ever find yourself in 2024 with this loop and a
slide deck, well, you know what to do.
